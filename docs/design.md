# Architecture

Ratatoskr keeps tool code separate from skill content. The content repository can be private; this public MIT repository contains no personal skills or machine profiles. The design was implemented independently without reading competitor code.

## Components

- `ratatoskr-core` parses and renders content, plans and applies owned files, manages source edits and adoption backups, inspects Git, generates OS schedules, reports failure/recovery alerts, and verifies helper updates.
- `ratatoskr-skill-sync` provides the `ratatoskr` one-shot CLI. An OS scheduler invokes `sync`; no desktop process or resident watcher is required.
- `ratatoskr-desktop` provides Tauri commands around the same core. The TypeScript/Vite UI edits local content, reviews diffs, configures schedules, and invokes the official Tauri updater. The helper is bundled as a sidecar.
- A content checkout provides portable sources and target definitions. Git credentials use the existing Git authentication mechanism; Ratatoskr stores no Git tokens.
- Local configuration/state holds source selection, project registry, manifests, OS locks, scheduler records, notification state, and adoption backups.

## Initialization and local state

CLI `init --source <DIR> --machine <ID>` connects an existing content checkout; `--create` creates one and `--remote <URL>` clones one. All three use the same core initialization path and accept `--state-dir <DIR>` to save an explicit absolute state directory.

Without `--state-dir`, initialization compares the config path with the platform's default config file. That default retains the platform's local-data `state/` directory. Any other config path uses an absolute `<config filename>.state/` sibling, including relative CLI `--config` paths and absolute `RATATOSKR_CONFIG` overrides. The platform comparison deliberately ignores the environment override: setting `RATATOSKR_CONFIG` must not turn a disposable config into the live workspace. Including the config filename keeps separate configs in one directory isolated and avoids sharing live state when a custom config sits beside the default config (whose config/data directories coincide on macOS).

This selection occurs only when creating a config. Existing configs retain their explicit `state_dir`, with no migration or fallback on load. The desktop's `connect_workspace` uses the same core for create, clone and connect; its default config and default state remain unchanged. A desktop launched with a custom `RATATOSKR_CONFIG` gets config-specific sibling state when connecting a new workspace.

See the [disposable preview example](usage.md#disposable-preview-configuration) for `plan` and `skill preview` from a content PR checkout. Initialization saves the config after validating a plan but does not apply outputs or create state. Isolated state does not change a profile's live output destinations; review the plan and use staging before applying to disposable outputs.

## Rendering and ownership

Global and project content share the selected machine and harness definitions. Conditions, variables, file variants, and harness frontmatter are resolved into an immutable desired-file map. Projects provide only skill content and a marker; they do not vendor the rendering tool.

Planning compares desired bytes and executable permissions against both live destinations and the ownership manifest. Applying checks all destinations before writing, rechecks each file, atomically replaces individual files, and writes the new manifest last. The UI submits the exact reviewed plan; the core compares it again under the apply lock.

Adoption backs up existing files and records their current fingerprints without rendering over them. Restore validates backup hashes and current ownership before writing. A source archive uses a same-volume rename; no recursive source deletion occurs. Unregistering a project detaches its owned output and leaves the project files intact.

On macOS and Linux, atomic replacement preserves the existing file's Unix mode, owner and group before publishing the new inode. Temporary files must prove owner-only access before any payload bytes are written. New files are owner-only (`0600`, or `0700` when executable), and new directories created by the writer are `0700`. Changing executable status does not grant additional read/write access. Backup snapshots retain optional mode/owner/group metadata; restore intersects saved and current permissions so later tightening remains effective. If no execute bit survives the intersection of two executable files, restore refuses during preflight rather than recreating denied execute bits. A deleted file can recover its saved group. Legacy backups without protection metadata use owner-only permissions, intersected with an existing destination's owner permissions; missing destinations use owner-only defaults. This applies equally to source and installed-file backups, since an existing public mode may be damage from an old release. Ownership manifest fingerprints remain compatible with previous versions.

This policy deliberately refuses protections it cannot reproduce: native macOS file ACLs, inheritable directory ACEs, directory deny-add/delete-child rules, Linux POSIX file access/directory default ACLs, special Unix mode bits, and files owned by another user. A group outside the process's groups is accepted only when a replacement naturally inherits that same group from its directory; otherwise writes and restore refuse before mutation. The checks run during apply/conflict/restore preflight and again at the write boundary; backup also checks all captured files before copying content. Non-inheritable directory ACLs stay on their directories: a normal macOS home-directory deny-delete ACE and Linux parent access ACLs are accepted. Immutable/append-only macOS files are refused. ACL inspection errors fail closed. Restore refuses changed owner/group identities rather than guessing. Other Unix platforms refuse writes because native ACL inspection is unavailable. Concurrent unrelated filesystem edits can still race final publication; a multi-file apply remains nontransactional.

`cfg(unix)` includes macOS, so the former unconditional `0644`/`0755` chmod exposed private files on a supported platform. Windows does not execute that chmod branch. Its existing tempfile replacement uses `MoveFileExW`, which does not establish preservation of an explicit/protected destination DACL or its owner. This Unix remediation does not change or validate that Windows security-descriptor behavior. Windows ACL preservation requires separate implementation and native acceptance; green cross-platform build/tests do not prove it. Linux core CI exercises ordinary mode/ownership behavior, while Linux desktop packaging remains unsupported.

The app keeps configuration and project-removal controls available when source preview fails. The failure remains visible and blocks apply. CLI failures exit nonzero.

## Background operation

A dedicated clean deployment checkout avoids scheduled pulls colliding with authoring edits. `sync` holds an OS-backed lock, performs a fast-forward-only pull, applies, handles optional standalone-helper updates, then reports success or failure through a deduplicated notification ledger. It retries apply on every invocation, even if Git has not changed. There is no watcher or per-project CI requirement.

Pushover and ntfy notifications require HTTPS for the initial request and every redirect. HTTPS redirects remain supported; an HTTP downgrade fails delivery and leaves the notification eligible for retry.

macOS sync uses launchd StartInterval and RunAtLoad. Its independent helper also monitors desktop update health, even when the desktop process has stopped. The macOS desktop remains resident when its window closes, reopens from the Dock, and exits on Quit/Cmd+Q. Opt-in login startup uses `--background`; disabled login startup remains disabled and Settings explains the resulting update availability. Windows sync uses a resident Rust tray controller and hidden login startup; owned legacy Task Scheduler jobs are migrated conservatively. The helper requires an available content volume, state directory, Git credentials, and PATH. Existing schedules belong to the current user and are removed only when their definition still matches the stored record.

## Updates

The independent CLI verifies a Minisign signature, then verifies the signed executable's reported version against the manifest before self-replacement. The native app uses the official Tauri updater and replaces the complete bundle, including its sidecar. A bundled helper never replaces itself independently. The official HTTPS release endpoint and public key are compiled into both applications. Explicit local fork overrides are visibly labelled. Nightly automatic updates default to midnight local time. One shared Rust task owns the update timer on all desktop platforms and reevaluates the wall clock every minute. Hidden WebViews and frontend JavaScript suspension cannot stop that timer. A missed window triggers a check on the next native tick, including after sleep or long uptime, and opens a persisted one-hour catch-up period. Ordinary nightly installation stays within the configured hour. The missed-window catch-up hour deliberately allows automatic installation and relaunch during the daytime when there are no unsaved edits or busy operations; installation is no longer restricted to the nightly window or app launch. Busy deferral never slides either deadline forward. Startup catches up before enabling editing and waits for helper operations; all installation paths retain signed-update verification. Automatic installation holds workspace locks, checks native UI busy state before installation, and rechecks it after the download. An edit begun during the request preserves the pending update for an idle retry. Relaunch follows installation only.

The app-data ledger persists attempts separately from successful checks, effective settings, pending installation, and catch-up start. Two completed nightly windows without success report an overdue desktop update through the existing desktop notification ledger, visible in `job-status`/Activity and the configured alert transport. On macOS the launchd helper owns overdue reporting independently of desktop lifetime; the desktop only reports actual check/install outcomes. Other platforms retain their resident watchdog after the check attempt. Specific check failures take precedence over a generic overdue alert. Existing specific desktop-update errors take precedence over generic overdue messages, preserving the cause and the existing 24-hour error deduplication and recovery behavior. Idle ticks and unsuccessful attempts do not recover health. Legacy ledgers start a grace period rather than treating attempts as proven successful checks. Manual checks contribute successful-check health only: they do not consume the automatic slot, open a catch-up installation hour, or persist an available update as pending for a later launch. The manual command clears any previously queued automatic update; the independent automatic schedule remains active. On macOS the monitoring baseline survives desktop restarts, so time with the app closed counts toward missed windows. The helper reads the desktop app-data ledger but never writes it; a separate helper-owned grace ledger gives missing/old successful-check metadata two completed windows before an overdue warning. Attempts are never inferred to be successes. CLI-only installations without desktop state or an existing watchdog are excluded. Corrupt state raises a monitoring failure. Notification read/decide/deliver operations hold a per-ledger OS lock, including the helper's health read, so desktop recovery and helper alerts share deduplication. Other desktop platforms retain their startup baseline.

The October 2026 failure investigation found that macOS invoked nightly policy only from a frontend 60-second interval, while both the desktop wrapper and core policy refused out-of-window checks except at launch. Deterministic tests reproduce the missing catch-up after a missed midnight and a 13:38 tick, and cover multi-day uptime, sleep, busy deferral, deadline expiry, persistence, and overdue diagnostics. WKWebView/App Nap throttling is a plausible trigger for the missing tick, not a demonstrated OS-level cause; the installed apps were left untouched.

The one-shot standalone helper records its last daily attempt and updates before sync; update failures and their alerts never prevent the content sync. Skipped daily checks retry pending notifications, including errors recorded before alerts were configured. Bundled helpers skip self-update and clear only the obsolete self-replacement error; unknown errors remain until a successful desktop update check clears bundled-helper health. Recovery is delivered once only for previously delivered problems. Update and sync notification ledgers are independent. Sync verifies the configured deployment branch (default `main`) and its remote upstream before any update, pull, or apply. The read-only desktop health check runs independently of that branch check, so a broken content checkout does not suppress update monitoring.

## Limits and review focus

A multi-file apply is not a filesystem transaction, and OS locks cannot stop unrelated editors. Source paths are trusted configuration but traversal, symlinks, collisions and ownership boundaries are checked. Source edits use hashes to detect stale editor state; a concurrent writer can still race the final file replacement. Project status uses the last local upstream reference.

Initial development focuses on macOS and Windows. Linux core checks are included, but Linux desktop packaging and scheduler installation are outside this draft. See the verification record for what has actually run.
