# Architecture

Ratatoskr keeps tool code separate from skill content. The content repository can be private; this public MIT repository contains no personal skills or machine profiles. The design was implemented independently without reading competitor code.

## Components

- `ratatoskr-core` parses and renders content, plans and applies owned files, manages source edits and adoption backups, inspects Git, generates OS schedules, reports failure/recovery alerts, and verifies helper updates.
- `ratatoskr-skill-sync` provides the `ratatoskr` one-shot CLI. An OS scheduler invokes `sync`; no desktop process or resident watcher is required.
- `ratatoskr-desktop` provides Tauri commands around the same core. The TypeScript/Vite UI edits local content, reviews diffs, configures schedules, and invokes the official Tauri updater. The helper is bundled as a sidecar.
- A content checkout provides portable sources and target definitions. Git credentials use the existing Git authentication mechanism; Ratatoskr stores no Git tokens.
- Local configuration/state holds source selection, project registry, manifests, OS locks, scheduler records, notification state, and adoption backups.

## Initialization and local state

CLI `init --source <DIR> --machine <ID>` connects an existing content checkout; `--create` creates one and `--remote <URL>` clones one. All three use the same core initialization path and accept `--state-dir <DIR>` to save an explicit absolute state directory.

Without `--state-dir`, initialization compares the config path with the platform's default config file. That default retains the platform's local-data `state/` directory. Any other config path uses an absolute `<config filename>.state/` sibling, including relative CLI `--config` paths and absolute `RATATOSKR_CONFIG` overrides. The platform comparison deliberately ignores the environment override: setting `RATATOSKR_CONFIG` must not turn a disposable config into the live workspace. Including the config filename keeps separate configs in one directory isolated and avoids sharing live state when a custom config sits beside the default config (whose config/data directories coincide on macOS).

This selection occurs only when creating a config. Existing configs retain their explicit `state_dir`, with no migration or fallback on load. The desktop's `connect_workspace` uses the same core for create, clone and connect; its default config and default state remain unchanged. A desktop launched with a custom `RATATOSKR_CONFIG` gets config-specific sibling state when connecting a new workspace.

See the [disposable preview example](usage.md#disposable-preview-configuration) for `plan` and `skill preview` from a content PR checkout. Initialization saves the config after validating a plan but does not apply outputs or create state. Isolated state does not change a profile's live output destinations; review the plan and use staging before applying to disposable outputs.

## Rendering and ownership

Global and project content share the selected machine and harness definitions. Conditions, variables, file variants, and harness frontmatter are resolved into an immutable desired-file map. Projects provide only skill content and a marker; they do not vendor the rendering tool.

Planning compares desired bytes and executable permissions against both live destinations and the ownership manifest. Applying checks all destinations before writing, rechecks each file, atomically replaces individual files, and writes the new manifest last. The UI submits the exact reviewed plan; the core compares it again under the apply lock.

Adoption backs up existing files and records their current fingerprints without rendering over them. Restore validates backup hashes and current ownership before writing. A source archive uses a same-volume rename; no recursive source deletion occurs. Unregistering a project detaches its owned output and leaves the project files intact.

On macOS and Linux, atomic replacement preserves the existing file's Unix mode, owner and group before publishing the new inode. Temporary files must prove owner-only access before any payload bytes are written. New files are owner-only (`0600`, or `0700` when executable), and new directories created by the writer are `0700`. Changing executable status does not grant additional read/write access. Backup snapshots retain optional mode/owner/group metadata; restore intersects saved and current permissions so later tightening remains effective. If no execute bit survives the intersection of two executable files, restore refuses during preflight rather than recreating denied execute bits. A deleted file can recover its saved group. Legacy backups without protection metadata use owner-only permissions, intersected with an existing destination's owner permissions; missing destinations use owner-only defaults. This applies equally to source and installed-file backups, since an existing public mode may be damage from an old release. Ownership manifest fingerprints remain compatible with previous versions.

This policy deliberately refuses protections it cannot reproduce: native macOS file ACLs, inheritable directory ACEs, directory deny-add/delete-child rules, Linux POSIX file access/directory default ACLs, special Unix mode bits, and files owned by another user. A group outside the process's groups is accepted only when a replacement naturally inherits that same group from its directory; otherwise writes and restore refuse before mutation. The checks run during apply/conflict/restore preflight and again at the write boundary; backup also checks all captured files before copying content. Non-inheritable directory ACLs stay on their directories: a normal macOS home-directory deny-delete ACE and Linux parent access ACLs are accepted. Immutable/append-only macOS files are refused. ACL inspection errors fail closed. Restore refuses changed owner/group identities rather than guessing. Other Unix platforms refuse writes because native ACL inspection is unavailable. Concurrent unrelated filesystem edits can still race final publication; a multi-file apply remains nontransactional.

`cfg(unix)` includes macOS, so the former unconditional `0644`/`0755` chmod exposed private files on a supported platform. Windows does not execute that chmod branch. Its existing tempfile replacement uses `MoveFileExW`, which does not establish preservation of an explicit/protected destination DACL or its owner. This Unix remediation does not change or validate that Windows security-descriptor behavior. Windows ACL preservation requires separate implementation and native acceptance; green cross-platform build/tests do not prove it. Linux core CI exercises ordinary mode/ownership behavior, while Linux desktop packaging remains unsupported.

The app keeps configuration and project-removal controls available when source preview fails. The failure remains visible and blocks apply. CLI failures exit nonzero.

## Desktop source publication

Desktop-owned source edits use one typed `DesktopSourceEdit` dispatcher, separate from the write-only core/CLI functions. `desktop_source_edit` acquires OS operation locks in the same order as sync followed by apply: `sync.lock` → `apply.lock`. Internal locked editor/conflict/restore implementations avoid recursive acquisition. Both guards remain alive through fetch/fast-forward, hash/preview validation, source writes, commit, local installation, and push. Manual Apply is excluded by `apply.lock`; background sync is excluded by `sync.lock`. Updater idle guards already take these locks in this order. A failed second acquisition releases the first.

The shared Git publisher reuses deployment validation and fingerprints only the selected operation's source scopes before and after writing. It stages individual changed paths with literal pathspecs and `git add -A`, then commits with `--only` so unrelated index entries cannot leak into the commit. Moves include their old and new paths; archive bytes are published alongside source deletions. An unchanged save creates no empty commit. Push uses an explicit deploy-branch refspec on its validated upstream remote, independent of custom `push.default`/remote push mappings. Normal user identity, signing, credentials, and hooks apply.

The snapshot plan and CLI status share `ContentStatus`: all central uncommitted files, outgoing commits against the local upstream reference, upstream name, and inspection error. A successful write returns `SourceEditResult` with an optional receipt path and typed independent installation/publication outcomes. Post-write commit, installation and push failures are explicit outcomes, not rejected saves; the UI clears saved drafts and retains the failure notice across refreshes. Pre-write failures still reject and preserve drafts. Push now retries existing commits. A commit failure prevents installation/publication; after a successful commit, installation failure never prevents push. Sync treats outgoing content commits as a persisted/alerted problem before applying. Save explicitly installs unpublished content before pushing. This is a deliberate exception to background sync's refusal to deploy unpublished commits: failed publication leaves the installation in place and sync keeps reporting/alerting until Push now succeeds. Installation renders the whole workspace, as sync does, whether or not background sync is active. Backup restoration (Undo resolution) never installs: it returns to the pre-resolution state, conflict included. Project edits install working-tree content and bypass publication; CLI source writers never invoke the desktop publisher. Configuration/setup/state/output-only commands are outside publication, except conflict resolution and backup restoration when they actually change central source files.

## Background operation

A dedicated clean deployment checkout avoids scheduled pulls colliding with authoring edits. `sync` holds an OS-backed lock, performs a fast-forward-only pull, applies, handles optional standalone-helper updates, then reports success or failure through a deduplicated notification ledger. It retries apply on every invocation, even if Git has not changed. There is no watcher or per-project CI requirement.

Pushover and ntfy notifications require HTTPS for the initial request and every redirect. HTTPS redirects remain supported; an HTTP downgrade fails delivery and leaves the notification eligible for retry.

macOS sync uses launchd StartInterval and RunAtLoad. The bundled helper owns automatic checks and headless installation; no resident desktop is needed. Interactive launch/Reopen creates a window and Regular activation policy. Close quits, with the frontend unsaved-changes prompt when needed. Headless launch uses Accessory activation policy and no webview. Old macOS login entries are disabled at launch. Windows retains its resident tray, windowless login startup and conservative legacy-task migration. Its main window is created on demand on a separate worker so WebView2 never blocks the event-thread message pump. Opens serialize get-or-create; showing runs on the event thread with a native liveness check, and an open racing destruction waits for Destroyed before rebuilding. Closing destroys the window and releases WebView2; native sync and updates continue in the tray. Only implicit last-window ExitRequested (code None) is prevented; Quit and restart carry explicit codes. Destroyed clears UI busy state, with native mutations still protected by their lock. Existing schedules belong to the current user and are removed only when their definition matches the record.

## Updates

The standalone CLI verifies the Minisign signature and signed executable version before self-replacement. The Tauri updater replaces the complete signed bundle including its helper. Official HTTPS endpoint/key defaults and explicit fork overrides are preserved.

On macOS, the helper checks when automatic updates are on, no success exists since the latest local nightly slot, and no attempt occurred in the last hour. Sleep catches up on the next tick. Effective settings, attempts, successes, error cause, pending release and install pacing live in `<state_dir>/<machine>/desktop-update-watchdog.json`. Non-due ticks do no network/process work and write only changes. No desktop scheduler ledger is read for health. The distinct new schema disregards old watchdog baselines and checks first on migration.

Pending releases defer while an app holds the desktop instance lock. Otherwise the helper reuses an unanswered request or writes one, persists launch pacing, and starts `--background` at most hourly. Unanswered/failed installs alert after an hour with their version and cause; spawn failures alert immediately. Pending clears when the helper's own version reaches the release. Standalone CLIs ignore all desktop state and clear obsolete monitoring errors.

Headless startup settles an old Installing response before processing requests, including a v0.2.21 predecessor relaunching the new executable. Lock contention retries every five seconds. No request means immediate exit. A 30-minute deadline records Failed and alerts; exit waits through active bundle replacement to avoid corrupting the app. ExitRequested is prevented only during installation. Reopen and interactive second launches create a window in the existing instance. The final restart decision runs on the main thread: windows restart visibly, windowless processes restart headlessly and settle/exit. Interactive macOS startup and the desktop run no automatic launch/nightly checks. Manual and explicit requests retain signatures, workspace locks and busy checks.

Two completed failed helper nightly windows alert with the last check error. Transient failures that recover hourly stay silent. Corrupt/unreadable state alerts as monitoring failure. Manifest success alone does not erase install failure. Notification read/decide/deliver holds a per-ledger OS lock; unchanged errors repeat after 24 hours and recovery is sent once for delivered problems. Windows retains its resident scheduler, startup baseline, nightly/catch-up installation hour and busy-state checks.

The standalone helper's daily self-update failures never prevent sync; skipped checks retry pending notifications. Bundled helpers clear the obsolete self-replacement error, while explicit desktop success can clear bundled-helper health. Update and sync outcomes are separate. The macOS helper update tick runs independently of deployment-branch validation so a broken checkout cannot suppress monitoring.

## Limits and review focus

A multi-file apply is not a filesystem transaction, and OS locks cannot stop unrelated editors. Source paths are trusted configuration but traversal, symlinks, collisions and ownership boundaries are checked. Source edits use hashes to detect stale editor state; a concurrent writer can still race the final file replacement. Project status uses the last local upstream reference.

Initial development focuses on macOS and Windows. Linux core checks are included, but Linux desktop packaging and scheduler installation are outside this draft. See the verification record for what has actually run.

## Local Save and attention decisions

`apply`, `apply_reviewed` and desktop Save share one `apply_locked` body. Public apply operations acquire their own guard; Save calls the body under its existing guard, avoiding a second non-blocking flock. The minute sync's no-change fast path still returns its preflight without rewriting the manifest or rendering again. Draft analysis/preview never invokes apply.

Operations with no central Git paths include installed-only conflict resolutions and backups without central source changes. They can alter output/ownership and therefore use write → install, without publication. A local install applies the current workspace, including monitored project working trees; it is not limited to the one source file just edited.

Needs attention keeps conflicts, former locations and legacy copies as explicit decisions. Pending files are read-only when background sync is active; manual Apply is available when it is off. A stale reviewed Apply returns the dedicated `PlanChanged` error carrying its fresh locked preflight, converted at the IPC boundary to a typed reply and neutral UI note. It never enters the global error banner or clears unrelated errors.
